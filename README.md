# Character Card Producer

### 把二次元角色蒸馏成写作用角色卡（Character Card）。

> *「不要替角色写。让角色决定自己怎么活，再由作者落笔。」*

[![Agent Skills](https://img.shields.io/badge/Agent%20Skills-Standard-green)](https://agentskills.io)
[![Runtime-Claude Code](https://img.shields.io/badge/Runtime-Claude%20Code-blueviolet)](#安装)
[![Local Research](https://img.shields.io/badge/Local%20Research-Moegirl%20API-orange)](#本地检索优先)
[![License: MIT](https://img.shields.io/badge/License-MIT-green.svg)](LICENSE)

<br>

**CCP 帮你把动画、漫画、游戏角色蒸馏成写作用角色卡，供 AI 辅助写作时作为参考规范引用。**

输入一个角色名和作品名，CCP 会完成资料检索、交叉验证、行为蒸馏、质量检查，生成一张带资料日期、来源边界和更新路径的 `character-card.md`。

这张卡让 AI 以**作者/叙述者**视角写出符合角色行为逻辑的场景、对白和内心戏，也用于**场景设计、剧本设计**，让 AI 设计的剧情、场景不至于 OOC。

## 效果示例

你不需要自己整理人设，也不需要写一大段 prompt。

只要说：

```text
> 生成千早爱音的角色卡
> 蒸馏丰川祥子（BanG Dream! Ave Mujica）
> 做一个《孤独摇滚！》后藤一里的写作用角色卡
```

生成后，写作 AI 会引用这张卡来写。以作者视角，而不是扮演角色：

```text
用户      ❯ 写一段：排练结束后人都走了，立希一个人留在录音室，
            看到灯落在桌上的笔记本，想起下午她差点又说"一辈子"。

立希把麦克风线一圈圈绕好，绕到最后一圈时，手指停在原地。
笔记本摊在调音台边上，摊开的那页写着歌词，字迹有点歪，像是电车摇晃时写的。

她没有去碰它。就站在那儿看了一会儿。

——灯那家伙，下午说完"一辈子"之后，自己先慌了。
明明每次都是这样。把太重的话先说出口，再把下一句吞回去。

（立希）"……笨。"

她弯下腰，合上笔记本，把卷起的角压平，塞回灯的包里。
然后关灯，锁门。走廊里的脚步声，比平时慢。
```

场景设计时，角色卡同样在起作用：

```text
用户      ❯ 设计一场戏：素世想私下挽留乐队，避免在正式场合摊牌。别让她 OOC。

设计稿要点：
- 场景目标：在不被拒绝的前提下，重新确认对方是否还想继续。
- 障碍：对方已经疲惫，不愿再谈；正式场合其他人会旁观。
- 选择：素世会用"关心对方"的方式切入，先不提乐队，只问近况——
  符合她"用绕路的方式维护关系"的行为模式。
- 核对反 OOC 清单：9/10 通过，第 5 条"决策一致"需回查……
```

这不是把台词拼起来。真正被蒸馏出来的是：**角色面对关系、压力、边界和选择时的行为逻辑，以及它在场景、对白、内心戏里如何落地。**

## 这张卡和普通角色卡有什么区别

普通角色卡常常这样写：

```text
性格：冷静、可靠、疏离。
说话方式：简短、理性。
```

这对写作 AI 来说太模糊。它知道标签，却不知道怎么落笔。

CCP 写的是：

```text
当别人要求她给出长期承诺时，她会先把关系翻译成任务：排练频率、退出条件、谁负责联络。
不是不在乎，而是用事务边界避免自己被卷入无法控制的情感期待。
```

区别就在这里：

| 普通角色卡     | CCP 写作用角色卡                            |
| -------------- | ------------------------------------------- |
| 写性格标签     | 写情境中的行为                              |
| 复述设定       | 蒸馏反应机制                                |
| 只够扮演聊天   | 供作者写出场景、对白、内心戏                |
| 没有设计约束   | 场景与剧情设计规范 + 反 OOC 检查清单        |
| 没有资料边界   | 记录资料检索日期和未覆盖内容                |
| 很难更新       | 可用 sources / manifest 追踪更新            |

**设定告诉你角色是什么。角色卡告诉作者：她会怎么活着、怎么说、怎么想。**

## CCP 蒸馏什么

CCP 提取六层信息：

| 层次                   | CCP 关心的问题                                                       |
| ---------------------- | -------------------------------------------------------------------- |
| **行为规范**     | 什么情境下会做什么？压力下如何变形？                                 |
| **对白写作规范** | 句子长短、停顿、口癖、自称、敬语层级如何落到台词？                   |
| **内心戏写作规范** | 她心里怎么想、哪些不会说出口、叙述者能看到多少？                     |
| **社会认知**     | 她默认怎么理解他人的善意、威胁、亲近和背叛？                         |
| **决策逻辑**     | 多个价值冲突时，她先保什么、牺牲什么？                               |
| **知识边界 + 资料时间边界** | 角色知道什么、资料检索到哪一天、新剧情发布后如何更新？ |

CCP 不追求更像百科。它追求让作者写出一个「像角色那样活着」的人。

## 产品哲学

CCP 的底层判断很简单：**角色不是资料页，而是一套可引用的反应系统。**

Wiki 告诉你角色经历了什么；普通角色卡告诉你角色大概是什么属性；CCP 要进一步回答：当这个角色被放进一个原作没有写过的新情境里，她会先注意什么、误解什么、保护什么、拒绝什么，又会用怎样的节奏把话说出口——并把这一切写成一份写作 AI 可以按需查阅的规范。

| CCP 要写进去的 | 意味着什么                         | 没写进去会怎样     |
| -------------- | ---------------------------------- | ------------------ |
| 行为镜片       | 角色先看见什么，忽略什么           | 只会复述设定       |
| 反应规则       | 何时靠近、逃开、攻击、沉默         | 所有场景都一个反应 |
| 表达 DNA       | 句长、停顿、敬语、自称、情绪泄露   | 只剩口癖表演       |
| 关系算法       | 如何判断善意、背叛、亲近、利用     | 对谁都一样热情     |
| 决策底线       | 价值冲突时先保什么                 | 角色被剧情推着走   |
| 内心戏边界     | 心里怎么想、哪些不说出口、读者能看到多少 | 内心戏写成作者旁白 |

**写得进去的是行为规范，写不进去的要变成边界。** 这不是降低写作自由度，反而是让角色更可信：真正像角色的人，不会什么都知道，也不会永远把话说完。

## 未来使用场景

CCP 不只是“生成几个角色”的工具。它更像是把角色从静态资料中解放出来，变成可以被同人创作、剧情试写、场景与剧本设计和互动叙事共同调用的写作参考层。

现在，它可以用于：

| 场景             | 怎么用                                   | CCP 提供什么                           |
| ---------------- | ---------------------------------------- | -------------------------------------- |
| 同人创作         | 写场景、对白、内心戏片段                 | 不只给台词，还给行为逻辑和叙述视角     |
| 剧情试写         | 把角色放进原作没有写过的新情境           | 用行为模式推断反应，而不是硬贴设定     |
| 场景 / 剧本设计  | 先设计剧情框架、对白节拍                 | 场景与剧情设计规范 + 反 OOC 检查清单   |
| OOC 审稿         | 把写好的草稿和角色卡逐项比对             | 定位偏离点并给出修改方向               |
| 长篇一致性       | 跨章节保持角色声音和决策稳定             | 角色速览 + 可追溯的行为规范           |

未来，它可以继续走向：

| 方向                       | 可能形态                                                      |
| -------------------------- | ------------------------------------------------------------- |
| AI 互动小说                | 角色不再只是 NPC 台词库，而是能根据玩家行动做出一致反应       |
| AI 视觉小说 / Galgame 原型 | 用角色卡驱动分支对白、好感变化、冲突升级                      |
| 多角色叙事实验             | 让不同角色卡在同一事件中碰撞，生成群像剧情                    |
| 创作者工作台               | 作者用 CCP 保持角色声音一致，快速试写场景、改写对白、检查 OOC |
| 可更新角色档案             | 作品出新剧情后更新资料日期和行为模式，让角色随作品成长        |

CCP 面向更多创作者提供一套可共享的角色写作基础设施。今天它服务同人写作与剧情设计；未来它可以成为 AI 互动小说、角色驱动游戏和二次元创作工具链的一部分。

## 本地检索优先

很多角色生成器依赖搜索插件、MCP 或浏览器能力。CCP 的方向是：**核心资料优先由本仓库脚本检索，外部搜索只是补强。**

当前已内置：

```bash
python scripts/source_search.py "高松灯" --work "BanG Dream! It's MyGO!!!!!" --mode discover
python scripts/source_search.py "能天使" --work "明日方舟" --sources moegirl
python scripts/moegirl_api.py "高松灯" --search
python scripts/moegirl_api.py "能天使" --full
```

目前本地检索重点支持萌娘百科 MediaWiki API，并通过统一的 `source_search.py` 输出结构化 JSON。其他站点 adapter 会逐步扩展；在 adapter 尚未实现时，CCP 会记录失败项，并允许用网页搜索、用户材料或其他来源补强。

这不是为了炫技，而是为了让生成结果可审计：

- 查了哪些来源；
- 哪些来源失败；
- 每条资料是哪天检索的；
- 是否命中黑名单来源；
- 之后作品更新时该从哪里重新检查。

## 使用

安装后，对 Claude Code 说：

```text
> /ccp
> 生成千早爱音的角色卡
> 蒸馏丰川祥子（BanG Dream! Ave Mujica）
> 做一个《孤独摇滚！》后藤一里的写作用角色卡
```

拿到角色卡后，写作时直接引用它：

```text
> 用这张卡写：爱音第一次来我家排练的片段
> 设计一场不会 OOC 的对手戏，用卡里的检查清单核对
> 我这段草稿会不会 OOC？帮我对照角色卡审一遍
```

CCP 会先确认角色和作品。如果你手上有设定集、访谈、BD 特典、字幕、截图或游戏剧情文本，也可以直接给它。用户提供的官方材料优先级最高。

## 工作原理

CCP 默认采用最高质量生成模式，不提供省 token 快速版。输入角色后，它会做六件事：

**1. 本地来源发现**
优先运行 `scripts/source_search.py` 和站点 adapter，检索萌娘百科、MediaWiki 系站点、作品 Wiki 等核心来源。搜索 skill / MCP 只作为补缺。

**2. 结构化来源索引**
生成 `references/sources.json`，记录 URL、来源等级、检索日期、失败项和可选 content hash。

**3. 五路并行分析**
设定与世界观、人格、表达质感、人际关系、关键场景分开调研，避免一个维度吞掉另一个维度。

**4. 行为蒸馏**
把资料从「发生过什么」提炼成「角色在类似情境下会怎么行动」。保留矛盾，不把角色磨平成稳定人设。

**5. metadata 与资料边界**
生成 `manifest.json`，记录角色、作品、覆盖媒体、资料检索完成日期、未覆盖内容、质量评分和 honesty boundary。

**6. 组装角色卡并验证**
按模板组装 `character-card.md`（含写作视角规则、场景与剧情设计规范、反 OOC 检查清单），再运行质量检查确认结构完整、视角正确、边界诚实。

```bash
python scripts/quality_check.py output/yahata-umiri/
python scripts/merge_research.py output/yahata-umiri/
python scripts/generate_manifest.py output/yahata-umiri/
```

完整方法论见：

- `references/distillation-framework.md`
- `references/character-card-template.md`
- `references/source-output-schema.md`

## 生成的角色卡长什么样

每个角色都是一个自包含目录：

```text
yahata-umiri/
├── character-card.md                  # 写作用角色卡（供 AI 作者引用）
├── manifest.json                      # 角色、作品、资料日期、质量分、覆盖边界
└── references/
    ├── sources.json                   # 来源索引、检索日期、失败记录
    ├── distillation.md                # 从资料到行为模式的蒸馏链
    ├── quality-report.json            # 自动质量检查结果
    └── research/
        ├── 01-setting.md              # 世界观、身份、外表
        ├── 02-personality.md          # 行为模式、矛盾
        ├── 03-expression.md           # 说话质感、语言标志、经典台词
        ├── 04-relationships.md        # 社会认知、关系动态
        ├── 05-key-scenes.md           # 关键场景、压力下的决策逻辑
        └── 06-media-coverage.md       # 跨媒体覆盖、未覆盖内容、时间线
```

复制整个目录即可分享或使用角色卡。

## 资料时间边界与更新

每张 CCP 生成的角色卡都必须记录资料检索日期。

当作品后续发布新剧情、新活动、新台词、访谈或设定修订时，旧角色卡可能无法覆盖。写作 AI 不会硬拗旧设定，而会说明：

```text
本卡资料更新至 YYYY-MM-DD，可能没有覆盖之后发布的内容。如果你有最新版 CCP，或可以提供新剧情 / 新资料链接，我可以帮你更新这张卡；这可能会消耗一些 Token。
```

更新已有角色卡时，CCP 会读取旧 `manifest.json` 和 `sources.json`，重新检索核心来源，只重蒸馏受影响部分，并更新资料日期和质量报告。

## 信息源原则

二次元角色资料很容易被二创、转述和社区印象污染。CCP 的原则是：

| 优先级         | 来源                                                                        |
| -------------- | --------------------------------------------------------------------------- |
| **最高** | 用户提供的官方设定集、访谈、BD 特典、字幕、截图                             |
| **高**   | 官方网站、官方角色介绍、官方剧情文本、萌娘百科、Wikipedia、作品 Fandom Wiki |
| **中**   | Bangumi、AniDB、游戏剧情、Bilibili 高质量专栏、Anime News Network、Bestdori |
| **低**   | 粉丝讨论、社区解读，必须标注为推测                                          |
| **排除** | 知乎、微信公众号、百度百科                                                  |

至少两个独立来源交叉验证。资料不足就写不足，不补脑，不编造。

## 路线图

已实现 / 当前版本：

- CCP meta-skill 主流程；
- 写作用角色卡模板（写作视角规则 + 场景与剧情设计规范 + 反 OOC 检查清单）；
- 萌娘百科 MediaWiki API 本地检索；
- 统一来源发现入口 `source_search.py`；
- 质量检查 `quality_check.py`；
- 调研摘要 `merge_research.py`；
- manifest 生成 `generate_manifest.py`。

计划中：

- 更多本地 adapter：Bangumi、Fandom、Wikipedia、Bestdori、BWIKI；
- `file_manager.py`：更新前备份、回滚、修订记录；
- `distill_prompt.py`：把角色卡导出为普通平台可用 prompt；
- 更完整的增量更新检查和 source diff。

不会假装已经完成。能本地检索的就本地检索，暂时做不到的就记录失败、标注边界、等待补强。
